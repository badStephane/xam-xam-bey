# Revue back-end : Xam Xam Bëy

Date : 2026-10-12. Mode Revue, lecture seule. Périmètre : migrations Supabase, RLS, Storage, appels client (`adminApi`, `useRevision`, `useCatalog`), scripts de contenu.

## Hypothèses et limites

- Aucun appel à la vraie base : les constats viennent du code et des migrations du dépôt. La configuration Auth du projet Supabase (confirmation d'e-mail, SMTP, URL de redirection autorisées, fournisseur mot de passe) n'est pas versionnée (`supabase/config.toml` absent) : les constats qui en dépendent sont marqués « à vérifier dans le tableau de bord ».
- BE-1 repose sur la règle documentée de Supabase Storage (« remove » exige les droits `select` et `delete` sur `storage.objects`). À confirmer par un test en staging avant correction.
- Historique git (19 commits) parcouru : aucune clé `service_role`, aucun JWT, aucun `.env` commité. `.env.local` est bien ignoré (`.gitignore:6`). `.netlify/state.json` ne contient qu'un `siteId`, qui n'est pas un secret.

## Ce qui est solide (vérifié)

- `progress` : lecture, création et mise à jour limitées à `auth.uid() = user_id` (`20261012120000_revision.sql:33-50`), `anon` révoqué. Aucun IDOR possible sur la progression d'un autre utilisateur.
- `cards` : un non-admin ne lit que `status = 'published'` (`20261012191639_library.sql:94-96`), `anon` n'a aucun droit (ligne 104). Les brouillons sont protégés côté serveur, pas seulement par le filtre client.
- `is_admin()` : `security definer`, `search_path = ''`, rattachée à `auth.uid()` et à `email_confirmed_at`, comparaison en minuscules des deux côtés, contrainte `email = lower(email)` sur `admins` (lignes 4-24). Repli fermé côté client (`adminApi.ts:26`).
- `documents` : écriture réservée aux admins, `created_by` masqué par les droits de colonne (lignes 55-58). Séquence recalée après la reprise (ligne 288).
- Storage : écriture limitée aux admins, nom de fichier contraint par regex, bucket limité à 50 Mo et `application/pdf` (lignes 61-73). Pas de politique `select`, donc pas de listage du bucket.

## Recommandations prioritaires

1. **BE-1 d'abord** : un test de 5 minutes en staging, une politique `select` sur le bucket et une vérification du résultat de `remove()`. C'est la seule faille qui laisse un document « retiré » accessible au public.
2. **Fusion serveur de la progression (BE-2)** par une fonction RPC, avec en même temps les bornes de taille de BE-6. Une seule migration couvre l'intégrité de la donnée et l'abus de quota.
3. **Une seule source de vérité pour les cartes (BE-3)** : passer le script en `do nothing`, et écrire l'ADR « la base fait foi, `data/seed` sert seulement d'amorçage ».
4. **Configuration Auth versionnée et durcie (BE-4, BE-7)** : SMTP externe, confirmation d'e-mail, fournisseur mot de passe désactivé, redirections strictes, le tout dans `supabase/config.toml`.
5. **Plus d'écriture admin silencieuse (BE-5)** : `.select('id')` et un contrôle du nombre de lignes sur chaque mutation, avec un test unitaire par fonction d'`adminApi`.

## Annexe : constats mineurs (BASSE)

- A1 `library.sql:104` : `cards` n'a pas de droits de colonne. Tout utilisateur connecté peut lire `created_by` (l'UUID des admins), alors que `documents` le masque. Appliquer le même `revoke select` puis `grant select (colonnes)`.
- A2 `useRevision.ts:92` : `progress.updated_at` est fourni par l'horloge du client, et aucun déclencheur `touch_updated_at` n'existe sur `progress`. Ajouter le déclencheur.
- A3 `revision.sql:53` : `delete` est révoqué sur `progress` et aucun parcours de suppression de compte n'existe. Le droit à l'effacement (loi 2008-12) passe donc par une intervention manuelle. Documenter la procédure ou ajouter une RPC `delete_my_account`.
- A4 `adminApi.ts:102-105` : la position d'une nouvelle carte est calculée par « lire le max puis insérer ». Deux admins simultanés obtiennent la même position. C'est sans gravité (tri seulement) ; une contrainte `unique (zone, position)` n'est pas nécessaire à moins de 5 admins.
- A5 `cardRules.ts:57` et `library.sql:62` : le type MIME est vérifié sur l'en-tête déclaré, pas sur le contenu. Le contrôle `countPages` est seulement côté client. Le risque est faible, car l'envoi est réservé aux admins.
- A6 `useRevision.ts:82-99` : en cas de changement de compte sans déconnexion, un `flush` en attente peut viser l'ancien `user_id`. La RLS le rejette, ce qui donne une boucle de nouvelles tentatives toutes les 10 s et perd les dernières notes de l'ancien compte. Annuler le minuteur dans `loadFor`.
- A7 `library.sql:148` : `revision_content` accepte encore les identifiants `cards-N` (regex `revision.sql:5`), devenus inutiles. Restreindre la regex à `plan|fiche-N`.
- A8 `library.sql:147` (document 32, « ETAT NOMINATIF ») : il est dans le bucket public. Vérifier qu'il ne contient pas de données personnelles réelles (question pour le PM).
- A9 Offre gratuite : un projet Supabase inactif est mis en pause. Les URL des PDF (`supabase.ts:25`) tombent alors, y compris en mode catalogue intégré. Point à transmettre au SRE (ping planifié ou repli `f/`).
- A10 `upload_documents.mjs:45` : le script est idempotent (`upsert: true`). Il utilise la clé `service_role` passée par variable d'environnement, sans écriture sur disque. Conforme.
